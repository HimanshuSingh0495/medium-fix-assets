Trust the Diff, Not the Demo: Coding Agents in Production

Subagent fan-out, review loops, and CI gates: an honest account of where coding agents help, where they create rework, and why verification is the whole job.

On a slow afternoon in September I gave a coding agent the most boring task on my board: migrate a pile of call sites from our old HTTP client to the new one. It was well specified. It was mechanical. It was exactly the kind of work agents are supposed to eat for breakfast. The agent fanned out subagents across the files and handed me a complete diff in minutes. It read beautifully. The commit messages were crisp, the changes were consistent, and the tests passed. Then I read it properly. Three call sites used the new client in ways that compiled fine and passed the suite but were subtly wrong: a retry policy configured backwards, an auth header attached at the wrong layer, a timeout that no longer applied to streaming calls. The agent had optimized for the shape of correctness, not correctness itself. That afternoon taught me the shape of this whole discipline. The agent was not useless and it was not magic. It was a fast engineer with perfect recall and no judgment, and it needed mine.

1. What a coding agent is, from first principles

This is the last article in the series, so let me state the definition plainly. An AI agent is a model wrapped in a loop: it perceives, it acts, it observes the result, and it repeats until the goal is done. A chatbot answers and stops. An agent works.

A coding agent applies that loop to a repository. It reads files, runs searches, edits code, runs the compiler, runs the tests, reads the failures, and tries again. Perception is the repo and the terminal output. Action is file edits and shell commands. Observation is every error message and test result.

That checkable loop is why coding became the natural habitat of agents before almost any other domain. Most agent tasks lack ground truth. A research agent can hand you a confident paragraph and you may never know it drifted. A coding agent runs into the compiler, the type checker, and the test suite, all of which say no without flinching. Code pushes back. That resistance is what makes the whole thing workable: the agent is not just generating, it is generating inside a machine that verifies.

But notice the limits of that machine. The compiler verifies syntax and types. The tests verify whatever the tests verify. Nothing in the loop verifies intent. My migration story passed every automated check and was still wrong in three places. The loop is necessary. It is not sufficient, and everything that follows is about closing the gap.

2. Subagent fan-out: parallelism with a parent in charge

The most useful structural idea in coding agents this year is the subagent. In Claude Code, a parent agent spawns worker agents: it decomposes a task, hands each piece to a worker, and merges the results. One parent plans, workers rewrite packages in parallel, the parent reviews the combined diff.

This is concurrency, and it has the same virtues and the same failure modes as concurrency everywhere else. Fan-out works when the subtasks are independent and well scoped: read-heavy reconnaissance across a large codebase, parallel test runs, applying the same mechanical change across isolated modules. It fails exactly where threads fail: shared mutable state. Two workers editing the same file produce merge conflicts and lost changes. Workers given vague interfaces drift apart and return pieces that do not fit. A parent that decomposes poorly hands out chaos in parallel, and you get the chaos back faster.

The decomposition quality is the ceiling. If you cannot state the task boundaries cleanly to another engineer, the parent agent cannot state them cleanly to its workers either, and no amount of parallelism fixes a bad split. I have learned to treat the parent's plan as the actual deliverable to review: read the decomposition before anyone writes code, the same way you would review a design doc before a team starts building.

3. The review loop is the job

The mental model that has served me best: the coding agent is a prolific junior engineer. Fast, tireless, enormous recall, zero judgment. You would never let a junior's code ship without review, and you would never let it ship because the diff looked tidy. Treat agent output the same way.

My review process is deliberately boring. I read every agent diff in full before it merges, the same way I would review a human's pull request. I require tests for anything behavioral. I make the agent explain changes it cannot justify, because that is the tell: when it cannot explain a choice, the choice was pattern matching, and pattern matching is where the backwards retry policies live.

Review is not overhead on agent work. Review is the work.

Sometimes the review plus the fix cycle costs more than writing the code myself would have. It happens with ambiguous specs, where the agent fills the gaps with plausible wrong choices and I have to unpick them. It happens with clever diffs that are hard to verify. When I notice I am spending longer verifying than I would have spent writing, I stop delegating that class of task and keep it for myself. That is routing: knowing which work is agent-shaped and which is not.

4. CI is the second reviewer

Human review catches intent. CI catches everything mechanical, and it never gets tired or charmed by a pretty diff. The rule is simple: agent-authored code flows through the exact same gates as human code. No shortcuts, no "the agent said it works," no merging on green vibes. A minimal gate looks like this:

name: agent-gate
on: pull_request
jobs:
  verify:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci
      - run: npm run typecheck   # the compiler says no
      - run: npm run lint       # style says no
      - run: npm test -- --coverage # the suite says no

This is also where the industry is heading, and September 2026 made the direction of travel unmistakable. Atlassian is reportedly now providing context and governance for AI coding agents: context so agents work against the right project knowledge instead of guessing, governance so organizations can see what agents are doing and set boundaries around it. Microsoft is reportedly using AI to review AI-generated code extensions: machine review aimed at machine-written code, at a scale humans cannot match.

Nobody is responding to the verification problem by trusting the agents more. They are building more verification: richer context up front, governance around the middle, automated review at the end. But it comes with a caution I would tape to every monitor: AI reviewing AI only works if the reviewer has independent ground truth. Tests, type systems, linters, and explicit policies are ground truth. A second model reading the same code and nodding along is confidence laundering. The September moves are interesting precisely where they add checks that do not share the agent's blind spots.

5. Where it helps, where it creates rework

After months of this, my honest ledger has two columns.

Agents help with mechanical, well-specified, easily checked work: migrations across many call sites, boilerplate, test scaffolding, bulk renames, exploring an unfamiliar codebase and summarizing what it does, first drafts of documentation. These tasks have clear done criteria and the verification is cheap. The agent does the typing and I do the reading, which is a good division of labor.

Agents create rework when the spec is ambiguous, because they fill gaps with the most plausible choice rather than the right one, and plausible wrong code is the most expensive kind to find. They create rework in cross-cutting refactors where one change ripples through assumptions the agent cannot see. They create rework in security-sensitive code when nobody with security judgment reads the diff. They create rework when teams skip review because the output looked right.

Plausible wrong code is the most expensive kind to find.

One tooling note, since it comes up constantly: do not reach for a general agent framework to do coding work. Coding agents live in a specific loop of read, edit, run, and observe, and coding-native tools are built around exactly that loop. A general framework adds abstraction layers between the agent and the repository without adding any of the affordances that make repo work fast: cheap file access, terminal feedback, diff review. Use the tools built for the job.

Coding agents, the short version

  • Decompose before you delegate. Parallel workers need independent, well-scoped tasks, and the parent's plan is the document to review first.
  • Read every agent diff in full. If you cannot afford to review it, you cannot afford to ship it.
  • Run the tests, then check the edges the tests do not cover. Compilers and suites verify mechanics, not intent.
  • Push agent code through the same CI gates as human code. No exceptions for machine authors.
  • Track rework, not just speed. If review plus fixes costs more than writing it yourself, that task was not agent-shaped.
  • Watch the September direction of travel: governance and context for agents (reportedly Atlassian) and AI-assisted review of AI-generated code (reportedly Microsoft). Verification infrastructure, not blind trust.
  • Use coding-native tools for repo work, not general agent frameworks. The loop is read, edit, run, observe.

Ten articles in, the thesis of this series has not changed since the first one. An agent is a model in a loop of perceive, act, and observe. In coding, that loop has the rare advantage of ground truth: compilers, tests, and reviewers that push back. September 2026 shows the industry converging on the same conclusion from every direction. More agents, more delegation, and crucially more verification around all of it. The verdict for 2026: coding agents are force multipliers with verification, and liabilities without it. The agent writes the code. You still ship it.
