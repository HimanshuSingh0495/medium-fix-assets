Your Tests Graded the Words; Production Grades the Actions

Why agents pass tests and fail in production: the eval gap between what an agent says and what an agent does, and how to close it.

This September, Gartner predicted that more than 40% of agentic AI projects will be scrapped by 2027. I believe it. Earlier this year I watched a customer support agent ace nearly every test conversation we put in front of it, then issue duplicate refunds and touch the wrong orders in its first week of live traffic. The evals were not wrong about the model. They were wrong about what they were testing. They graded the agent's words. Production graded its actions. The distance between those two things is the eval gap, and it is where most agent pilots go to die.

1. An agent is a loop, not a sentence

Strip an agent to first principles and you get three things. A model that generates the next token. Tools that turn tokens into effects: API calls, database writes, messages sent, money moved. And state that the tools mutate. The loop runs like this: take a goal, plan one step, call a tool, read the observation, repeat until done or give up. The model proposes. The loop disposes.

This is the entire difference between a chatbot and an agent. A chatbot lives in text, so testing its text is testing the system. An agent's state is not the conversation. It is a database row, a queue, a customer's balance. Test only the text and you have tested the proposal, not the effect. Everything the agent actually does happens in the gap between its final message and the transcript you graded.

2. The eval that passes is grading the wrong thing

Most agent evals work like this: hand the agent a scenario, mock the tools, grade the final answer against an expected answer. The mock returns clean JSON, instantly, every time. This tests whether the agent can write a good plan and a good closing message. It does not test whether the agent can execute anything, because nothing was executed. The tool calls hit fixtures, not services.

Here is what those evals structurally cannot see. The right tool called with the wrong arguments. The right tools called in the wrong order. An observation misread: the refund tool succeeded on attempt one and the agent retried it anyway. A plan that was perfect against a snapshot of state that changed before the first call landed. None of this appears in a transcript graded for textual similarity to a golden answer.

A test that grades the final answer and never replays the tool calls is testing a different system than the one you ship.

And the coverage is thinner than the industry admits. In LangChain's 2026 survey of more than 1,300 professionals, only 52% run offline evals at all, and only 37% run online evals against production behavior. Nearly a third cite quality as their number one barrier. We are grading the easy half of the system and skipping the hard half.

3. What production adds: state, failure, and money

Production gives the agent three things the lab never did. First, state that moves. Between the plan and the tool call, the world changes: the ticket gets reassigned, the inventory count drops, the second order on the account is the one the customer meant. The agent acts on a memory of the world, not the world.

Second, tools that fail in shapes the mocks never had. Timeouts. Partial writes. A 200 OK with an error body. Rate limits that arrive as a different status code every Tuesday. Offline fixtures are deterministic and polite. Production tools are neither.

Third, side effects that compound. One action changes the state the next action reads. Two individually correct steps can compose into one wrong outcome: the refund call timed out, so the agent retried it, and both attempts posted. The eval never replayed the retry path, because the fixture never timed out. Reliability degrades fast as workflows grow: per industry data from mid-2026, multi-agent reliability across workflows with 4 or more tool calls drops under 65%. Every additional action is another chance for state, failure, and money to disagree with the plan.

Agents rarely fail because the model is confused. They fail because the world moved between the plan and the tool call.

4. The pilot graveyard, in numbers

September 2026 is a good month to take stock, because the industry numbers are unusually blunt. Eighty-eight percent of enterprise agent pilots never reach production. When teams are asked what blocks them, the top answer is not the model: eval and observability gaps lead at 64%, followed by governance at 57% and model reliability at 51%. A 2026 systematic review puts it more starkly still: fewer than 24% of pilots reach operational status. And Gartner expects more than 40% of agentic AI projects to be scrapped by 2027.

Read these together and the pattern is plain. The industry did not fail to build agents that work in demos. It failed to build the machinery that proves they work in production: evals that exercise actions, observability that shows the tool-call trace, governance that bounds what the trace is allowed to touch. The graveyard is full of agents that were never tested as agents.

5. Test the loop, not the output

The fix follows from the diagnosis. If the system is a loop, the eval must run the loop.

  1. Run the full loop in evals, tools included. Not mocks with canned JSON: a stateful sandbox the agent can actually read from and write to. If the agent can issue a refund in production, it must be able to issue one in eval, against fake money and real state.
  2. Assert on the trace and the end state, not the final text. Which tools were called, with which arguments, in which order. What did the world look like when the run ended. The final message is the least informative artifact of an agent run.
  3. Replay every scenario multiple times. Agents are nondeterministic. A scenario that passes once and fails one time in five is a production incident with a timer on it.
  4. Inject tool failures as first-class scenarios. Timeouts, partial writes, reordered results, schemas that changed overnight. The eval suite should contain every failure shape production has ever shown you.
  5. Sample production and grade it. Take real traces, replay the interesting ones, and grade the actions with a critic model that checks each tool call against the state at the time it was made. The emerging pattern is automated verification harnesses and synthetic evals with critic models, reportedly cutting human review hours by 70% or more. Review the trace, not the transcript.
def run_action_eval(agent, scenario):
    world = reset_sandbox(scenario.seed)      # real state, fake money
    trace = agent.run(scenario.prompt, world)  # tools hit the sandbox
    return {
        # end state and trace, not final text
        "goal_met": world.check(scenario.goal),
        "tool_calls": trace.calls,           # tool, args, order
        "side_effects": world.unintended(), # mutations outside the goal
        "spend": trace.total_spend(),
    }

for scenario in eval_suite:            # scenarios include tool failures
    for attempt in range(3):           # nondeterminism is a first-class input
        grade(run_action_eval(agent, scenario))

Before the first live call

  • Tools run in evals against a stateful sandbox. Canned fixtures alone do not count.
  • Assertions cover the tool-call trace and the end state, not just the final answer.
  • Every scenario replays at least three times. Flaky once is flaky in production.
  • Tool failures are explicit scenarios: timeouts, partial writes, changed schemas, reordered results.
  • Mutating tool calls carry idempotency keys. A retry never double-posts.
  • Production traces are sampled weekly and graded by a critic model against the state at call time.
  • Every tool has a timeout, a spend cap, and a kill switch. All three, before launch.

The model is not the system. The loop is the system, and the loop is what ships. Grade the words and you get a chatbot that aces demos. Grade the actions and you get an agent you can trust with a refund button at 2am. September's numbers say the industry is learning this the expensive way. Run the loop in your evals and you can learn it the cheap way.
